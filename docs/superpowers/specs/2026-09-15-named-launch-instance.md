# Named Launch Instance (`--instance`) Technical Spec

**Design Brief:** `/home/sf/worlds/personal/designs/hcom/named-launch-instance.md` (Status: approved)
**Status:** sound
**Repo:** `/home/sf/workspace/hcom`

## Intent (from the Brief — do not rewrite)

> Worlds `ensureLead` / `launchArgv` still passes `hcom omp --name
> <four-letter>` expecting that to be the minted instance name. On this fork
> that is CALLER identity, not the child.

> Add a launch-only flag that fills `LaunchParams.name`. Do not steal
> `--name`. Do not treat inherited `HCOM_INSTANCE_NAME` as a mint request.

> Flag spelling: `--instance <name>`. Help on every launch tool. `hcom omp
> --name midi --instance reko --go` mints `reko` and attributes the launch to
> caller `midi`.

Brief acceptance (quoted):

1. "`hcom omp --instance <free-four-letter> --go` mints that name (row +
   `HCOM_INSTANCE_NAME`). Not a random generated name."
2. "`hcom omp --name <caller> --instance <child> --go` still mints `<child>`;
   `--name` is launcher identity (`HCOM_LAUNCHED_BY` / reply handoff)."
3. "Name held by listening/active/blocked → fail closed (existing
   `resolve_explicit_name_conflict`)."
4. "`--instance` with count > 1 → fail (already in launcher)."
5. "Help lists `--instance` on launch tools. README one line if launch flags
   are documented there."
6. "No worlds writes. Midi updates `launchArgv` after the SHA."

Preserve (quoted): "`--name` stays caller identity on launch, send, start
(subagent agent-id), everything else." "`hcom start --as` stays reclaim, not
launch mint." "Fork/resume `LaunchParams.name` path unchanged."

## Mapping onto the current system

All claims **observed** in the repo unless marked otherwise.

- The mint hook already exists. `LaunchParams.name: Option<String>`
  (`src/launcher.rs:198`) is consumed by `launcher::launch`
  (`src/launcher.rs:1642`): explicit-name + count>1 bails
  (`src/launcher.rs:1781-1787`), live-name conflicts fail closed via
  `resolve_explicit_name_conflict` (`src/launcher.rs:1489`, rejects
  listening/active/blocked rows, allows free names, consumes inactive resume
  rows, passes through pending fork placeholders), and the child env gets
  `HCOM_INSTANCE_NAME` (`src/launcher.rs:1940`). Only the fork/resume path
  fills `name` today (via `instance_names::reserve_generated_name`,
  `src/commands/resume.rs:731`).
- Public launch never fills it: `src/commands/launch.rs:198` is
  `name: None, // --name is caller identity, not instance name`. This is the
  single seam the Brief asks to open.
- Launch argv parsing: `parse_launch_argv` (`src/commands/launch.rs:448`)
  skips leading `--name`/`--go`, reads count + tool, then
  `extract_launch_flags` (`src/commands/launch.rs:574`) pulls hcom-level flags
  (`--tag`, `--terminal`, `--device`, `--dir`, `--headless`, `--hcom-prompt`,
  `--hcom-system-prompt`, `--batch-id`, `--run-here`) out of the remaining
  argv, both `--flag value` and `--flag=value` forms. `--instance` joins this
  set as a new `HcomLaunchFlags.instance: Option<String>` field
  (`src/commands/launch.rs:433`).
- Caller identity is untouched: `resolve_launcher_name`
  (`src/commands/launch.rs:310`) reads `GlobalFlags.name` (the router's
  `--name`) and feeds `LaunchParams.launcher` / `HCOM_LAUNCHED_BY`. No change.
- Remote launch (`--device`): `run()` dispatches a JSON param bundle
  (`src/commands/launch.rs:84-94`) to `relay::control::handle_remote_launch`
  (`src/relay/control.rs:752`), which builds its own `LaunchParams` with
  `name: None` (`src/relay/control.rs:793`) from `RemoteLaunchRequest`
  (`src/relay/control.rs:680`, parsed by `from_params` via `optional_param`).
- Help: tool launch help is generated by `generate_tool_help`
  (`src/commands/help.rs:697`) from `SHARED_LAUNCH_FLAGS`
  (`src/commands/help.rs:972`) plus a launch-only `--device` line
  (`src/commands/help.rs:742-745`). `SHARED_LAUNCH_FLAGS` is also rendered by
  `resume_fork_help` (`src/commands/help.rs:990`), so launch-only flags must
  NOT be added to that constant.
- README documents launch flags in a table (`README.md:312-322`), so
  acceptance 5 requires one row there.

## Architecture

One new launch-only CLI flag threaded through two existing seams:

```
argv ──► parse_launch_argv / extract_launch_flags   (src/commands/launch.rs)
           │  HcomLaunchFlags.instance: Option<String>
           ▼
         run()
           ├─ local:  LaunchParams { name: flags.instance, .. }   (was None)
           └─ remote: params JSON gains "name"
                        ▼
              RemoteLaunchRequest.name (optional_param)
                        ▼
              handle_remote_launch: LaunchParams { name: request.name, .. }
                        ▼
              launcher::launch  (UNCHANGED: count>1 bail,
                                 resolve_explicit_name_conflict,
                                 HCOM_INSTANCE_NAME, row mint)
```

No launcher changes. No router changes (`--instance` is not a global flag; it
flows to the launch command in the remaining argv exactly like `--tag`). No
resume/fork changes.

## Components and interfaces

1. **`HcomLaunchFlags`** (`src/commands/launch.rs:433`) — add
   `pub instance: Option<String>`.
2. **`extract_launch_flags`** (`src/commands/launch.rs:574`) — add
   `--instance <name>` and `--instance=<name>` arms, mirroring `--tag`.
3. **`parse_launch_argv`** (`src/commands/launch.rs:448`) — after flag
   extraction, reject an empty/whitespace-only `--instance` value with
   `bail!` (fail closed; an empty name would mint a nonsense row). No charset
   validation beyond that — the Brief does not ask for one and the fork path
   applies none.
4. **`run()` local path** (`src/commands/launch.rs:198`) — replace
   `name: None` with `name: hcom_flags.instance.clone()`; update the stale
   comment to note `--name` remains caller identity and `--instance` is the
   mint request.
5. **`run()` remote path** (`src/commands/launch.rs:84-94`) — add
   `"name": hcom_flags.instance` to the dispatch params JSON.
6. **`RemoteLaunchRequest`** (`src/relay/control.rs:680`) — add
   `name: Option<String>`, parsed with the existing
   `optional_param(params, "name")` helper; `handle_remote_launch`
   (`src/relay/control.rs:793`) passes it to `LaunchParams.name`.
7. **`generate_tool_help`** (`src/commands/help.rs:697`) — push a
   `--instance <name>` line into the "hcom Flags" section alongside the
   launch-only `--device` line (NOT into `SHARED_LAUNCH_FLAGS`, which is
   shared with `hcom r` / `hcom f` help where the flag is not accepted).
   Description: mint this name for the launched instance; conflicts fail.
8. **README.md** (launch flags table, ~line 316) — one row:
   `--instance <name>` | Mint this name for the launched instance (fails if taken).

## Data / control flow

- `hcom omp --instance reko --go`: router extracts `--go`; launch command
  parses `instance = Some("reko")`; `LaunchParams.name = Some("reko")`;
  launcher validates (free name, count == 1), mints row `reko`, child env
  carries `HCOM_INSTANCE_NAME=reko`. No `generate_unique_name` fallback for
  the named instance (existing launcher behavior when `name` is `Some`).
- `hcom omp --name midi --instance reko --go`: router's `--name` feeds
  `resolve_launcher_name` → `LaunchParams.launcher = "midi"`
  (`HCOM_LAUNCHED_BY`, reply handoff); `--instance` feeds
  `LaunchParams.name = "reko"`. The two channels never meet.
- `hcom 2 omp --instance reko`: launcher bails "Cannot use explicit name with
  count > 1" (existing, `src/launcher.rs:1782`).
- `hcom omp --instance <taken>`: `resolve_explicit_name_conflict` errors
  "already exists" for listening/active/blocked rows (existing,
  `src/launcher.rs:1489`); inactive resume rows are consumed and pending fork
  placeholders pass through — unchanged existing semantics.
- Remote: `hcom omp --device <dev> --instance reko --go` forwards `"name"` in
  the relay params; the remote side applies the same launcher validation.

## Error handling

All fail-closed, mostly existing:

- Live name conflict → `resolve_explicit_name_conflict` error (existing).
- count > 1 with `--instance` → launcher bail (existing).
- Empty/whitespace `--instance ""` → `parse_launch_argv` bail (new, 3 lines).
- Remote relay to an older hcom that predates the `name` param: the old
  `from_params` ignores unknown keys, so the name is silently dropped and a
  generated name is minted. Recorded as an implementation consequence, not a
  requirement — same shape as any cross-version relay skew.

## Testing (behavioral contracts; exact tests live in the plan)

- Parse: `--instance reko` and `--instance=reko` both yield
  `flags.instance == Some("reko")`, are order-independent with tool args, and
  are not forwarded as tool args. `--instance ""` errors.
- Remote request: `RemoteLaunchRequest::from_params` round-trips `name`;
  absent `name` stays `None` (existing default test extended or sibling).
- Help: `get_command_help("omp")` contains `--instance`;
  `get_command_help("r")` does NOT (flag is launch-only).
- Launcher behavior (conflict fail-closed, count>1 bail, placeholder
  pass-through) is already covered by existing `launcher.rs` tests
  (`resolve_explicit_name_conflict_*`, lines 3584-3629); no duplication.
- End-to-end (lead/verifier): `hcom omp --instance <free-four-letter> --go`
  shows the minted name in `hcom list` and the child has
  `HCOM_INSTANCE_NAME` set; `hcom omp --name <caller> --instance <child>
  --go` attributes the launch to `<caller>`.

## Non-goals

- Changing `--name` meaning anywhere (launch, send, start, …).
- Treating inherited `HCOM_INSTANCE_NAME` as a mint request.
- `hcom start --as` semantics (stays reclaim).
- `hcom-fu2` (send-side self-assert hole) — untouched, not closed.
- Resume/fork flag surface (`hcom r` / `hcom f` do not gain `--instance`).
- Router/global-flag changes; TUI launch surface changes.
- Worlds repo writes; bouncing midi/kilo/reko/hera; leftover-pane cleanup.
- Charset/format validation of the instance name beyond non-empty.

## Implementation approach chosen (and rejected internals)

**Chosen:** thread `Option<String>` from `extract_launch_flags` through both
`run()` launch paths into `LaunchParams.name`, with the remote relay param
forwarded as an optional key. All Brief behavior (conflict fail-closed,
count>1 bail, child env, row mint) is already implemented in
`launcher::launch`; this spec only opens the public CLI seam.

Rejected internals (all would still satisfy the letter of the Brief but lose
on YAGNI/consistency):

- *Bail when `--instance` combines with `--device`* — invented restriction;
  forwarding follows the existing pattern for `tag`/`terminal`/prompts and
  keeps one semantic: `--instance` always names the launched child.
- *Add `--instance` to `SHARED_LAUNCH_FLAGS`* — that constant also renders in
  `hcom r` / `hcom f` help, advertising a flag resume/fork do not parse.
- *Silent ignore on remote* — violates the Brief's fail-closed spirit.
- *Retarget `--name` or consume inherited `HCOM_INSTANCE_NAME`* — explicitly
  forbidden by the Brief.

## Open questions

None. (Remote pass-through vs bail is an internals-only choice, decided above
in favor of pass-through; the Brief is silent on `--device` and both satisfy
every stated invariant.)
